APIculture is a developer portal for the same apiary / hive / inspection domain, exposed through several API styles. Each style has its own machine-readable contract.

## Architecture

A typical **REST** client–server setup. **Your application is the client**; **APIculture is the server**. The client never talks to the data store directly. SOAP, JSON-RPC, gRPC, GraphQL and WebSocket use the same split with a different payload and contract.

<ArchitectureDiagram />

| Piece | Role |
| --- | --- |
| **Client** | Your backend (or an SDK running on it). Holds the API key and talks to one of the protocol hosts. |
| **Server** | APIculture, behind a style-specific URL (`/v1`, `/soap/v1`, `/rpc/v1`, `/graphql`, `wss://…`). |
| **Data store** | Apiaries, hives and inspections owned by the account behind the key. Not reachable except through an API. |
| **Events** | REST [webhooks](/rest/guides/webhooks/) for account-wide HTTPS delivery; [WebSocket](/websocket/) for per-hive channels. |

### Request path (REST)

1. The client sends `Authorization: Bearer ak_…` over HTTPS to the sandbox or production host.
2. The server authenticates the key, applies the resource to the store, and returns JSON (or a [Problem Details](/resources/errors/) error).
3. On a relevant change the server sends a signed `POST` to your webhook URL. See [Webhooks](/rest/guides/webhooks/).

Browsers and mobile apps must **not** hold a key — they would expose it. Call the API from your server. Details: [Authentication](/getting-started/authentication/).

### Base URLs

| Environment | Base URL | Keys |
| --- | --- | --- |
| Local sandbox | `http://127.0.0.1:8787/v1` (`npm run sandbox`) | any `ak_test_…` |
| Hosted sandbox | `https://sandbox.api.apiculture.example/v1` | `ak_test_…` |
| Production | `https://api.apiculture.example/v1` | `ak_live_…` |

The [local sandbox](/getting-started/sandbox/) has the same HTTP surface as the contracts, uses isolated in-memory data per key, and never sends real webhook POSTs. The `*.apiculture.example` hosts are documentation defaults, not this repository.

## Data model

The API is organised around three resources owned by an **account** (the beekeeper or organisation that owns the API key).

<DataModelDiagram />

| Resource | Identifier prefix | Description |
| --- | --- | --- |
| Apiary | `ap_` | A physical site with a name and optional coordinates. |
| Hive | `hv_` | One colony in one hive box. Belongs to exactly one apiary and carries a [lifecycle status](#hive-lifecycle). |
| Inspection | `in_` | An immutable record of a visit to a hive: queen seen, brood frames, temperament, notes. |
| Webhook endpoint | `wh_` | An HTTPS URL that receives REST [events](/rest/guides/webhooks/). |

### Identifiers

Identifiers are strings composed of a resource prefix and a 26-character [ULID](https://github.com/ulid/spec), e.g. `hv_01J8Z5P2M3N4B5V6C7X8Z9A0S1`. They are unique across all accounts, sort chronologically, and are safe to use as URL path segments. Do not rely on their length or format beyond the prefix.

### Mutability

- Apiaries and hives can be updated (REST: `PATCH`).
- Inspections are **append-only**. A mistaken inspection is corrected by recording a new one; the history is never rewritten.
- Deleting an apiary is refused while it still contains hives — move or delete the hives first.

### Timestamps and dates

- `*_at` fields are RFC 3339 timestamps in UTC with a `Z` suffix.
- Date-only fields such as `queen_installed_at` use `YYYY-MM-DD` and have no time zone.
- `created_at` is set by the server; `inspected_at` is supplied by you and may be in the past.

## Hive lifecycle

Every hive has a `status` field describing the state of the colony.

| Status | Meaning |
| --- | --- |
| `active` | A healthy colony with a laying queen. The default for new hives. |
| `queenless` | No queen was seen in recent inspections and no eggs are present. |
| `swarmed` | Most of the colony left with the old queen. |
| `dead` | The colony died. The hive box may be reused by creating a new hive. |
| `archived` | Hidden from default lists. Terminal state. |

### Transitions

<HiveLifecycleDiagram />

- Status changes are made by the beekeeper in the app or via the API (REST: `PATCH /hives/{hiveId}`); the API never changes a status on its own based on inspection data.
- `archived` is terminal. Archived hives are excluded from default lists unless asked for explicitly.
- Every change emits a `hive.status_changed` event ([REST webhooks](/rest/guides/webhooks/) or [WebSocket](/websocket/reference/)).
